# 阶段 07：反爬策略与登录态复用

## 阶段目标

- 建立"反爬 ↔ 对抗"的完整认知地图，知道每类手段的边界与风险；
- 读懂 `core/browser_session` 可插拔模块的设计（这是全项目架构最完整的模块）；
- 掌握 Cookie 的导出 / 加密 / 注入 / 复用全链路；
- 守住合规红线：复用本人会话、不绕验证码、不伪造身份。

## 7.1 反爬与应对地图

| 站点手段 | 原理 | 本项目的应对（边界内） |
|---|---|---|
| UA 检查 | 识别非浏览器客户端 | UA 池轮换 + 真实浏览器 UA（`utils/user_agents.py`） |
| 频率限制 | 请求过快触发限流/封禁 | 延迟抖动、`rate_limit` 每分钟上限 |
| Referer 防盗链 | 媒体直链要求来源页 | 浏览器渲染携带真实 Referer；`extractor/network.py` 转发请求头 |
| IP 封禁 | 单 IP 高频 | 代理支持（住宅代理优先） |
| 登录墙 | 内容需登录 | **复用本人已登录会话**（本阶段主题） |
| 指纹检测 | 识别"像机器"的浏览器 | 指纹一致性 + 行为拟人化（**只降误判，不承诺绕过**） |
| 验证码 | 人机校验 | **不做任何绕过**——送登录页给使用者人工完成 |

> 红线：项目的反检测只做"指纹一致性"与"行为拟人化"，目的是**降低被误判为机器人的概率**，不承诺、也不实现绕过任何风控审核。这是学习与实战都必须坚持的边界。

## 7.2 `core/browser_session` 模块架构

定位：框架内的**可插拔模块**，统一入口 `load_browser_session(config)`，生命周期钩子（初始化/健康检查/销毁）由 `registry.py` 暴露。

| 子模块 | 职责 |
|---|---|
| `config.py` | `SessionConfig`、平台默认路径探测（Win/macOS/Linux 的 Chrome/Edge User Data）、环境变量 `CRAWLER_SESSION_*` 覆盖、路径校验 |
| `launcher.py` | `BrowserLauncher`：带 User Data 启动、**占用检测**（读进程命令行，不凭锁文件误报）、健康检查 |
| `cookie_store.py` | `CookieStore`：导出 / 加密持久化 / 加载 / 注入 / 规范化（容忍过期时间五种写法、`sameSite` 别名、`__Host-` 前缀） |
| `session_bridge.py` | `SessionBridge`：登录态桥接到 requests / Playwright / 框架抓取层 |
| `login_state.py` | `LoginStateChecker`：判定规则优先级、三条检测通道、失效重登入口 |
| `anti_detect.py` | `AntiDetection`：反检测脚本、行为拟人化、代理接入 |
| `adapters.py` | `SeleniumDriver` / `PlaywrightDriver`：同一套驱动接口的两个实现，可注册自定义驱动 |
| `exceptions.py` | 自定义异常，消息全部"可操作"（告诉你下一步做什么） |
| `registry.py` | `ModuleRegistry`：模块注册、统一入口、生命周期钩子 |

**架构学习点**：

1. **契约一致**：`SessionHandle.fetch()` 与 `BaseFetcher.fetch()` 契约一致，可把登录态句柄直接当抓取器插进既有流水线；
2. **驱动解耦**：上层只面对 `BrowserDriver` 抽象，Playwright/Selenium 可互换；
3. **失败要可操作**：所有异常消息都包含"下一步怎么做"，拒绝静默失败；
4. **只读自检**：`python -m core.browser_session` 不起浏览器、不写文件，探测本机环境。

## 7.3 登录态检查：规则与三通道

判定优先级（命中即返回）：

1. **登出选择器/关键字**（最强负信号：出现"请先登录"，任何正向信号不足采信）；
2. **登录选择器/关键字**（出现即有效）；
3. **状态码**（`login_status` 命中即有效）；
4. **兜底**：Cookie 是否过期，结果标 `fallback=True` 并建议补齐规则。

三条检测通道（自动选择，可强制）：

| 通道 | 条件 | 特点 |
|---|---|---|
| `browser` | 有运行中的浏览器 | 最准：能跑选择器、看最终 URL；但读不到 HTTP 状态码 |
| `http` | 无浏览器但有 Cookie | 快，无 JS 渲染 |
| `cookie` | 都没有 | 静态兜底 |

> 常见坑：浏览器通道 `status=0` 导致 `login_status` 规则失效——此时应改用元素级选择器规则（`.login-form` / `.user-avatar`）。

## 7.4 Cookie 安全

- 导出默认**加密落盘**（`cryptography` 的 Fernet；口令经 SHA-256 派生，只存本地）；
- 密钥用环境变量 `CRAWLER_SESSION_KEY`；缺库或没口令时**降级明文并在日志与 `store.notes` 明确标注**，绝不静默；
- `resources/sessions/` **不应提交到版本库**——Cookie 等同账号凭据；
- 只想带同站 Cookie：`cookie_accept: same-site`。

## 7.5 两个最高频的坑

1. **User Data 独占**：Chromium 对同一 `--user-data-dir` 独占，复用前必须**完全退出**目标浏览器（含任务栏后台驻留进程）。项目主动检测并明确报错，而不是静默失败。不想关浏览器 → 用 Cookie 导出/导入方案；
2. **headless 与登录态冲突**：无头实例无法附着已有 Profile，退出时会与图形实例争抢 Profile 锁、互相覆盖 Cookie。复用登录态保持 `headless=false`；确需无头用 `impersonate=true` 显式承担风险，或复制 Profile 副本。

另：代理 IP 必须与时区/地理位置一致（"IP 在美国、时区 Asia/Shanghai"本身就是强风控特征）。

## 7.7 动手练习

1. **只读自检**：`python -m core.browser_session`，看懂本机浏览器 / User Data / 驱动 / 加密依赖的探测结果；
2. **最小示例（实时模式）**：完全退出 Edge/Chrome 后运行
   `python examples/browser_session_minimal.py --domain example.com --browser edge --check-url https://example.com/`；
3. **纯 Cookie 模式**：`--export-only` 导出一次，再 `--cookie-only` 复用，对比两种模式的启动差异；
4. **代码级复用**：按 README §2.1 写 15 行代码：`load_browser_session` → `get_driver` → `check_login` → `export_cookies` → `get_requests_session().get(...)`；
5. **加密体验**：设置 `CRAWLER_SESSION_KEY` 导出一次，再卸载口令读文件，观察 `CookieDecryptError` 的明确报错；
6. **占用检测**：浏览器开着直接运行示例，复现 `BrowserAlreadyRunning`，读懂报错里的解决步骤；
7. **合规自查**：用自己的话写出"本模块不能做什么"清单，与 README §1 对照。
