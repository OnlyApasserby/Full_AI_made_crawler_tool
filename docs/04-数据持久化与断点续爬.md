# 阶段 04：数据持久化与断点续爬

## 阶段目标

- 掌握 SQLite 在爬虫中的角色：URL 台账、任务状态、媒体资产、合规报告；
- 理解断点续爬的完整机制：指纹主键 + 任务状态 + 已抓集合加载；
- 能读懂并扩展 `manager/db_manager.py` 的表结构。

## 4.1 为什么爬虫需要数据库

爬虫是"长任务 + 易中断 + 需复盘"的典型场景：程序会崩、网络会断、目标会变。没有持久化，每次重启都从零开始；有了数据库，**已做的工作才是资产**。项目把 SQLite 作为集中存储（`resources/crawler_cache.db`），所有模块通过 `manager/db_manager.py` 单点访问。

## 4.2 表结构设计

| 表 | 关键字段 | 作用 |
|---|---|---|
| `crawled_urls` | `url_hash` 主键、`task_id` | URL 台账：抓过哪些页；`url_hash` 唯一 = 天然去重 |
| `crawl_tasks` | 任务 ID、`status`（running/completed） | 任务状态：断点续爬的"书签" |
| `media_downloads` | 媒体下载记录 | 下载了什么、到哪一步 |
| `media_items` | URL、类型、分辨率、时长、合集 | 媒体资产清单（导出 CSV/JSON/Markdown 的数据源） |
| `compliance_reports` | 站点、时间戳、报告路径 | 合规筛查留档，支持同站历史对比 |

设计要点：

- **`url_hash` 作主键**：插入冲突即"已抓过"，`INSERT OR IGNORE` 一行代码同时完成去重与登记；
- **任务级隔离**：`task_id` 让多任务各自拥有独立台账，互不污染；
- **WAL 模式 + `busy_timeout`**：WAL（Write-Ahead Logging）让读写不互斥，`busy_timeout` 让并发写入排队而不是立即报 `database is locked`——多线程爬虫写库的两个必备设置；
- **`ensure_schema` 兼容旧库**：建表 + 给旧库补列（`ALTER TABLE ADD COLUMN`），升级不丢数据。

## 4.3 断点续爬原理

```
首次爬取：create_crawl_task() 生成任务ID → 边爬边写 crawled_urls / crawl_tasks.status=running
    │
中断（崩溃/手动停止）
    │
重启：按任务ID resume → create_crawl_task(resume_task_id=旧ID)
    │
    ├─ load_visited_hashes(task_id) 载入已抓指纹集合
    └─ crawler 双去重直接命中 → 跳过已抓页面，只补未抓部分
    │
完成：crawl_tasks.status=completed
```

要点：

- **续爬 = 复用任务 ID**：`create_crawl_task(resume_task_id)` 不是新建任务，而是接着旧书签写；
- **已抓集合前置加载**：开爬前一次性 `load_visited_hashes`，爬行中只查内存集合，不逐条查库；
- **任务级 DB 隔离**：多任务场景下每个任务有独立数据库/目录/日志（阶段 08）。

## 4.5 动手练习

1. **看库**：跑一次真实爬取后，用 `sqlite3 resources/crawler_cache.db ".tables"` 与 `.schema crawled_urls` 查看结构，`SELECT COUNT(*) FROM crawled_urls` 对账；
2. **续爬实验**：深度设为 3 抓一个站点 → 中途强制结束进程 → 重启同任务 → 对比重启前后日志：已抓页面不应重复出现（可给页面抓取打时间戳计数验证）；
3. **schema 设计**：纸面设计一个"断点续爬下载器"的最小表（URL、文件路径、已下载字节数、总大小、MD5、状态），说出哪几个字段组合保证"重启后接着下"；
4. **WAL 体验**：两个 Python 进程同时写同一 SQLite 库，先不开 WAL 观察 `database is locked`，再开 WAL + `busy_timeout` 观察行为差异；
5. **迁移体验**：给 `crawled_urls` 加一列（如 `fetched_at`）的 `ALTER TABLE` 写法，验证旧数据不丢。
